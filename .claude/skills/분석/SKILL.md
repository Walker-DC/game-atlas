# /분석 — 게임 아틀라스: 게임 전체 분석과 방향 설정 (범용)

입력: $ARGUMENTS (첫 단어가 게임 이름, 나머지가 이번 회차 지시)

사용자가 이 명령을 입력한 것 자체가 `game-atlas` 워크플로우 실행에 대한 명시적 동의다. 방식 전체는 `분석_방식.md`에 있다.

## 1. 사전 확인 (짧게)
- `게임/<게임이름>/설정.json`과 `추출/요약.md`가 있어야 한다. 없으면 `/새게임`을 먼저 하라고 안내하고 멈춘다.
- `설정.json`에 템플릿 문구("게임 이름", "/mnt/c/..." 등)가 남아 있으면 그 칸만 사용자에게 묻는다.
- `게임/<이름>/결과/` 아래 가장 최근 회차 폴더의 `분석결과_원본_*.json`이 `base`다. 없으면 빈 문자열이고, 첫 회차라 기초 조사 5갈래가 먼저 돈다.
- 이번 회차 지시를 `note`로 정리한다. 확정 결정은 "확정:"으로 시작하는 줄로 적는다.
- `note` 끝에 `CLAUDE.md` "등록된 게임" 표의 추출 상태를 한 줄로 붙인다(예: `추출 범위: 부분 — 본체 game.zip 미추출·.jsc 암호화, 한글 문자열만`). '없음' 주장을 검증할 때 쓴다.
- **이전 회차 사실 점검**: `base` 결과에 `verification`이 없으면(검증 단계 도입 전 회차), 실행 전에 `도구/근거_대조.py`로 이전 결과를 대조하고, 판정을 받친 사내 사실(출시·종료 일정, 퍼블리싱 주체 등)은 사용자에게 먼저 확인한다. 확인 결과는 "확정:" 또는 "이전 회차 오류:" 줄로 `note`에 넣는다.
- **원작 조사 보충**: 이어하는 회차(`base` 있음)인데 `설정.json`의 `origin`에 원작명이 있고 `게임/<이름>/자료/원작조사_원본.json`이 없으면, 워크플로우 args에 `"research": ["원작"]`을 넣어 원작 갈래만 추가로 돌린다.
- 사용자가 새 자료를 줬으면 `게임/<이름>/자료/`에 복사하고 `설정.json`의 `materials`에 추가한다.

## 2. 워크플로우 실행
`Workflow` 도구를 `name: "game-atlas"`로 호출한다. `game`에는 설정.json 내용을 객체 그대로 넣는다(문자열 금지).

```json
{ "home": "<작업 폴더 절대경로>/게임/<이름>", "game": { ...설정.json... }, "note": "<지시>", "base": "<이전 json 절대경로 또는 빈 문자열>", "maxRounds": 24, "research": [], "mediateAfter": 3, "verify": true, "debateModel": "sonnet", "strongModel": "opus", "org": "<회사 이름>" }
```

- 모델: 설계자·검토자는 `debateModel`(기본 sonnet), 기초 조사·사실 검증·판정자는 `strongModel`(기본 opus). 모델이 달라야 같은 착각을 함께 할 가능성이 줄어든다. 사용자가 바꾸라고 할 때만 바꾼다.
- `org`: 분석을 맡긴 회사 이름. 이 이름이 든 사실은 웹으로 검증하지 않고 "사내 확인 필요"로 사용자 결정 항목에 올린다.
- `verify`(기본 true): 사실 검증. 사용자가 검증을 빼 달라고 할 때만 false.
- **종료 조건**: 설계자·검토자·판정자 셋이 모두 동의해야 끝난다. 검토자가 전 관점을 승인하면 사실 검증 → 판정자 최종 확인을 하고, 판정자가 고칠 것을 내면 설계자가 반영한 뒤 검토자가 전 관점을 다시 승인해야 한다. `maxRounds`는 폭주 방지용 안전장치일 뿐이다.

실행 직후 사용자에게 한두 줄로 알리고, 진행 상황은 `/workflows`에서 볼 수 있다고 덧붙인다.

## 2-1. 중재 요청 (stopReason이 `needs_mediation`일 때)
워크플로우는 같은 쟁점이 다시 오가면 설계자·검토자 모두 이전과 다른 근거·대안을 내도록 요구한다. 그래도 설계자가 같은 설계를 유지하고(`sameDesign`) 검토자가 같은 반대를 새 근거 없이 되풀이한(`sameObjection`) 왕복이 연속 `mediateAfter`번(기본 3) 쌓이면 **판정자가 원본을 확인해 먼저 판정**하고(검토자 / 설계자 / 절충), 그 판정은 확정 결정으로 반영돼 분석이 이어진다. 어느 한쪽이라도 새 근거·새 대안을 내면 0부터 다시 센다. 검토자가 새 id로 같은 취지를 다시 내도(`repeatOf`) 같은 쟁점으로 센다. 교착만으로는 멈추지 않는다(중재를 끈 경우만 교착 종료).

사용자 중재로 멈추는 경우는 둘뿐이다.
- 판정자가 사내 사정(예산·인력·계약·내부 일정)이 걸려 정할 수 없다고 넘긴 쟁점
- 설계자가 판정자 판정에 새 근거로 이의를 `mediateAfter`번 거듭 낸 쟁점(`disputes`의 `target`이 "판정자 판정") — 이때 "검토자 주장" 자리에 판정자 주장을 쓴다

1. 회차 폴더를 만들고(없으면) 워크플로우 결과 전체를 `중재대기_<k>.json`(k=1부터)으로 저장한다. 결과 정리(HTML 등)는 하지 않는다.
2. 터미널 첫 줄에 `⏸ 중재 요청 (<N>차에서 멈춤)`을 쓰고, `disputes`의 쟁점마다 아래를 쓴다.
   - 쟁점: 무엇을 두고 다투는지 한 줄(대상 plan 항목 포함)
   - 검토자 주장 / 설계자 주장: 각각 최근 근거 중심으로 두세 줄
   - 몇 번 오갔는지
   - 메인 세션 의견: 어느 쪽 근거가 더 강한지, 절충안이 있으면 그것
3. 마지막에 "중재 내용을 보내 주시면 이어서 진행합니다"라고 쓰고, 예시 형식을 한 줄 준다(예: `R3-2는 검토자 안으로, R5-1은 설계자 안 유지하되 1차 범위에서 뺌`). 다른 쟁점(`unresolved`)이 남아 있으면 개수만 알린다.
4. 그 자리에서 멈추고 사용자 답을 기다린다. 임의로 중재하지 않는다.

## 2-2. 중재 받아 이어가기
사용자가 중재 내용을 보내면(다음 세션이어도, `/분석` 없이 그냥 보내도) 그것이 이어서 실행하라는 동의다.
- 가장 최근 `중재대기_<k>.json`을 읽어 `resume` 객체를 그대로 넣고, 사용자 말을 `mediation`에 넣어 워크플로우를 다시 실행한다. `home`·`game`·`note`·`base`·`maxRounds`·`mediateAfter`는 처음 실행과 같게 한다.

```json
{ "home": "...", "game": { ... }, "note": "<처음 지시>", "base": "<처음과 같게>", "maxRounds": 24, "mediateAfter": 3, "resume": { ...중재대기 json의 resume... }, "mediation": "<사용자 중재 내용 그대로>" }
```

- 기초 조사와 첫 설계안은 다시 돌지 않는다. '설계자: 중재 반영' 한 단계 뒤 라운드 번호를 이어서 분석을 계속하고, 중재로 확정된 결정(`settled`)은 이후 라운드에서 다시 제기되지 않는다.
- 또 멈추면 2-1을 반복한다(`중재대기_<k+1>.json`).
- 사용자가 "그만", "여기서 정리" 식으로 답하면 다시 실행하지 않고, 최근 중재대기 json으로 3단계 결과 정리를 한다. 종료 사유는 `⚠️ 중재 대기에서 종료`.

## 3. 결과 정리
- 회차 폴더 `게임/<이름>/결과/<YYMMDD>_<N>회차/`를 만들고, 결과를 `분석결과_원본_<YYMMDD>.json`으로 저장한다.
- **근거 대조(필수, 정리 전에)**: `python3 도구/근거_대조.py 게임/<이름> <원본 json> --out <회차 폴더>/근거대조_<YYMMDD>.md`. 로컬 파일 근거(행 번호·인용·자리표시자)를 기계적으로 대조한다. '인용 불일치'·'자리표시자 의심'이 판정·진단·1차 항목에 걸리면 메인 세션이 원본을 열어 확인하고 결과 정리에 반영한다.
- **정리 단계 금지 규칙**(메인 세션이 판정·HTML·Word를 쓸 때 — 같은 착각이 정리 단계에서 다시 생기지 않게):
  - `final`·`verification`·`judge`에 없는 사실을 새로 넣지 않는다. 메인 세션이 직접 확인해 넣는 사실은 그 자리에 근거(파일명 L행 "인용" 또는 URL)를 단다.
  - 판정 이유 문장마다 근거와 검증 상태(V번호, 확인됨 / 과장 / 일부만 / 다름 / 못 찾음 / 추정 / 사내 확인 필요)를 단다. 달 수 없는 문장은 쓰지 않는다.
  - "추정:"·"사내 확인 필요"·검증에서 과장·다름으로 나온 것은 단정으로 바꾸지 않는다. 검토자·판정자가 미검증이라고 짚은 사실과 사내 사실은 판정 이유로 쓰지 않고 "전제" 칸에만 둔다.
  - 판정 문서를 쓴 뒤 `--doc <문서>`를 붙여 근거 대조를 다시 돌리고, '근거 없는 문장'을 고친다.
- 중재를 거친 회차면 합쳐서 저장한다: `research`·`initialDesign`은 `중재대기_1.json`에서, `rounds`는 중재대기 파일들과 마지막 결과를 순서대로 이어 붙이고(`verification`은 마지막 결과의 것), 각 중재(`disputes`·사용자 중재 내용·`mediation.applied`)를 `mediations` 배열로 넣는다. 나머지는 마지막 결과 그대로. 중재대기 파일은 지우지 않는다.
- 첫 회차라면 `research`를 `게임/<이름>/자료/기초조사_원본.json`으로도 저장하고, `설정.json`의 `materials`에 "1회차 기초 조사(5갈래)"로 추가한다. 다음 회차는 기초 조사를 다시 돌지 않기 때문이다.
- 원작 갈래만 추가로 돌린 회차라면 그 결과를 `게임/<이름>/자료/원작조사_원본.json`으로 저장하고 `materials`에 "원작 조사(<국가>, <원작명>)"로 추가한다.
- 같은 폴더에 내부용 HTML을 만든다(`<이름>_방향분석_내부용_<YYMMDD>.html`). 구성은 아래와 같다.
  - **성공 가능성 판정**(맨 위): 판정·확신도·이유·성공 조건. `final.outlook`을 쓰고, 판정자 판정(`judge.last.outlook`)을 나란히 둔다(합의로 끝났으면 같아야 한다 — 다르면 표시). 이전 회차 JSON처럼 없으면 메인 세션이 결과를 근거로 써서 '메인 세션 작성'이라고 밝히고, 위 정리 단계 금지 규칙을 그대로 따른다.
  - **판정자 기록**: 판정자가 판정한 쟁점(`judge.log`의 dispute — 쟁점·판정 쪽·이유), 최종 확인 회차별 승인 여부와 요구 변경, 설계자 이의와 답
  - **근거 대조**: `근거대조_<YYMMDD>.md`의 집계와 주요 항목
  - **근거 검증**: 상태별 집계(확인됨 / 과장 / 일부만 / 다름 / 못 찾음 / 근거 없음 / 사내 확인 필요 / 확인 불가), 설계자 반박 재검증(`verification.reverify`), 확인됨이 아닌 항목 표(주장·쓰인 곳·설계안 근거·원본 실제 내용·확인한 곳), 설계자 수정 내용, 판정이 바뀌었으면 전후(`verification.outlookBefore`)
  - 장르 판정
  - 제출안 판정표(있을 때)
  - BM 점검표
  - 진단
  - 컨셉
  - 핵심 루프
  - 개발 항목(펼침)
  - 결정 필요 사항
  - 남은 쟁점
  - 기초 조사 요약(첫 회차)
  - 중재 기록(있을 때): 쟁점, 양쪽 주장, 사용자 중재, 반영 결과
  - 라운드별 과정(중재 지점 표시)
- 터미널 출력:
  - 맨 첫 줄에 종료 사유를 쓴다. 합의(설계자·검토자·판정자 모두 동의) / ⚠️ 교착 / ⚠️ 안전장치 도달 / ⚠️ 에이전트 오류 / ⚠️ 중재 대기에서 종료 중 하나다. 합의가 아니면 판정자의 마지막 판정을 함께 쓴다. 중재를 거쳤으면 "(중재 N회)"를 덧붙인다.
  - **성공 가능성**: 판정(성공 / 조건부 성공 / 실패)과 확신도를 한 줄로 쓰고, 이유와 '어떻게 하면 성공하는지'를 짧게 쓴다. 에이전트 판정과 메인 세션 판단이 다르면 둘 다 쓴다.
  - **판정자**: 쟁점 판정 몇 건(어느 쪽으로), 최종 확인을 몇 번 거쳐 승인했는지, 판정자 요구로 바뀐 것
  - **근거 대조**: 집계 한 줄과 판정에 걸린 항목
  - **사실 검증**: 집계 한 줄, 핵심 근거 중 틀린 것과 고친 내용, 검증으로 판정·확신도가 바뀌었는지. `verification`이 없으면(중재 대기 정리·검증 끔·이전 버전 결과) "사실 검증 안 함"이라고 쓴다.
  - 지난 회차 대비 바뀐 점
  - 제출안 판정 집계(있을 때)
  - 최종 방향 핵심
  - 사용자 결정 항목: 중복을 합치고 권고를 함께 쓴다.
  - **자료 한계**: APK에서 못 읽은 부분, "추정:" 근거 비중
  - **반대측 관점 결과**: 큰 방향을 바꾸자는 제안이 있었는지, 어떻게 처리됐는지
  - **메인 세션 의견**: 두 에이전트가 함께 틀린 부분이 있으면 반드시 지적한다(예: 1차 범위 과다, 근거 없는 수치).
- 라운드별 과정은 HTML에만 두고, 터미널에는 요약만 쓴다.

## 4. 전달용 문서 (요청 시에만)
- **전달용은 항상 Word(.docx)로 만든다.** A4로 회차 폴더에 `<이름>_개선방향_<audience>전달용_<YYMMDD>.docx`로 저장한다. docx 스킬(`anthropic-skills:docx`)이나 python-docx를 쓴다.
- 문서 구성:
  - 한눈에 보는 변경 요약
  - 성공 가능성과 성공 조건
  - 왜 이 장르 기준인가
  - 현재의 구멍
  - 제출안 검토(있을 때)
  - 수정 방향
  - 돈 흐름도(PNG)
  - 상점·상품
  - 1차 범위
  - 함께 정할 것
  - 근거: 사실 검증에서 확인된 근거와 확인 안 된 전제(다름·못 찾음·근거 없음·확인 불가)를 나눠 쓴다
- 쉬운 말로 쓰고, 내부 G번호 같은 용어는 쓰지 않는다. 퍼블리셔 내부 손익·비용, 유저 닉네임, 라운드별 과정은 넣지 않는다.
